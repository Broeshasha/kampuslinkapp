KAMPUSLINK - CHAT TRANSLATION PLAN (FREE, 1-2 MINUTE DELAY)          2026-10-17
================================================================================
GOAL     Every chat message is stored in its ORIGINAL language, and the other
         languages (Arabic / French / English) are filled in by a background job within
         about 1-2 minutes. Readers see the message in their own language, with
         "see original". Cost target: zero during the pilot.
STATUS   Plan only. Nothing here is built. The DB side (file 09) and the Worker code
         come after you approve the decisions in section 10.

--------------------------------------------------------------------------------
1. WHAT ALREADY EXISTS (built and tested in the backend)
--------------------------------------------------------------------------------
  - module_chat_messages  (original text + lang: ar / fr / en / und)
  - message_translations  (message_id, lang, body, provider; one row per language)
  - get_chat_messages()   returns the translation for the reader's language when it exists
  - message_translations is in the realtime publication: a new translation row reaches
    the app live, no refresh needed
  - app_config / push / reminders: not involved
  MISSING: the job that creates the translation rows. That is this plan.

--------------------------------------------------------------------------------
2. FREE ENGINES (checked 2026-10-17; limits change, re-check before launch)
--------------------------------------------------------------------------------
  A  Cloudflare Workers AI, model @cf/meta/m2m100-1.2b          <- RECOMMENDED
       free: 10,000 "neurons" per day (resets 00:00 UTC), included in the Workers Free plan
       model price: 31,050 neurons per million tokens in, same per million out
       you already use Cloudflare (R2, Workers); no extra account; runs inside a Worker
       with a cron trigger. As far as I know no payment card is needed on the free plan.
       If the daily allowance is used up, calls fail until the next reset (handled below).
  B  Azure AI Translator, free F0: 2 million characters per month, no expiry.
       needs an Azure account with an INTERNATIONAL credit card (a problem in Algeria).
       Backup engine if you can get a card.
  C  Google Cloud Translation: 500,000 characters per month free, billing must be enabled
       (it charges automatically after the free part). DeepL API Free: also 500,000/month;
       check that it supports Arabic before relying on it. Too small for chat.
  D  On-device Google ML Kit translation (Flutter plugin): free, works offline, Arabic is on
       its list, but each language model is about 30 MB to download (data cost for students)
       and quality is lower. Optional fallback only, not the main engine.
  NOT USED: unofficial "free Google Translate" endpoints (against their terms, can be
       blocked at any time).

--------------------------------------------------------------------------------
3. THE NUMBERS (why engine A fits the pilot)
--------------------------------------------------------------------------------
  10,000 neurons/day  /  (31,050 + 31,050 neurons per million tokens)  =  ~160,000 source
  tokens per day that can be translated for free.
  An average chat message is ~20-30 tokens (Arabic a bit more), so:
     ~6,000 single translations per day (one target language each)
     with 1.3 targets per message on average (see rule 5.1)  =>  ~4,500 messages per day
  A cohort of 100-150 students sending ~20 messages a day = 2,000-3,000 messages a day.
  => Fits, with little headroom. These are my estimates: measure with the usage table.
  If you outgrow it: Workers Paid is $5/month base and about $0.68 per million tokens
  round trip (about 40,000 messages), so even paid it stays very cheap.

--------------------------------------------------------------------------------
4. THE FLOW (what happens to one message)
--------------------------------------------------------------------------------
  1. Student sends a message. post_chat_message() stores the ORIGINAL (lang from the app's
     script guess, or 'und') with translate_state = 'pending' and translate_after = +20 s
     (so a quick delete/edit does not waste a translation).
  2. A Cloudflare Worker with a CRON TRIGGER every 1 minute wakes up.
  3. It calls the service function claim_translation_batch(25): the DB hands out up to 25
     pending messages (newest first, last 24 h, "skip locked" so two runs never take the
     same message) together with the target languages each one needs.
  4. For each message the Worker: cleans it, detects the language, skips what needs no
     translation (section 5), looks in translation_cache, and only then asks the model.
  5. It calls save_translations() with the results: rows go into message_translations,
     the detected language is corrected, translate_state becomes done / skipped / failed.
  6. Realtime pushes the new translation row to every open chat. The bubble switches to the
     reader's language by itself.
  Timing: wait 20 s + wait for the next minute tick (0-60 s) + 1-5 s of work
          => about 20-85 seconds. That is inside your 1-2 minute target.
  If the daily free allowance is gone: the Worker puts messages back to 'pending'
  (retry after 00:00 UTC) and the app simply keeps showing the original.

--------------------------------------------------------------------------------
5. HOW WE STAY FREE (rules inside the Worker)
--------------------------------------------------------------------------------
  5.1 TRANSLATE ONLY INTO LANGUAGES THAT ARE USED. module_reader_languages(module) lists
      the preferred_language of the students who see that module. If nobody reads English
      there, English is not generated. For a mining cohort this is often just ar + fr, so
      one translation per message instead of two. (Run block M4 of file 08 to see yours.)
      If someone later switches language, the app asks request_translation(message, lang)
      and the Worker fills the gap on its next run (that one jumps the queue).
  5.2 SKIP what does not need translating: emoji-only, numbers, links, very short text
      (under 3 letters), formulas, and any message already in the target language.
  5.3 CACHE: translation_cache(text_hash, lang, body). "merci", "ok", "c'est où ?"
      repeated by many students cost nothing after the first time.
  5.4 CHUNK long text by sentence (max ~500 characters per model call).
  5.5 BUDGET GUARD: translation_usage(day, calls, chars, neurons_estimate). The Worker
      stops at ~90% of the daily allowance and warns you; it never gets cut off blindly.
  5.6 RETRIES: max 3 attempts with growing delay, then translate_state = 'failed'
      (the app keeps the original; an admin can retry).

--------------------------------------------------------------------------------
6. LANGUAGE DETECTION AND THE HONEST LIMITS
--------------------------------------------------------------------------------
  Detection is done in the Worker, for free, with simple rules:
     Arabic letters dominate            -> ar
     Latin letters: count French vs English common words  -> fr or en (tie -> und)
     Latin letters mixed with 2 3 7 9 inside words ("salam 3lik", "kifach 7alek")
        -> Arabizi / Darija in Latin letters -> 'und'
  What this means in practice:
   - ARABIZI AND DARIJA are NOT translated reliably by any free engine. Those messages are
     stored with lang 'und' and show the original with a small note. This will happen a lot
     in student chats. Decide later if a stronger (paid or larger-model) engine is worth it
     for Darija.
   - MINING TERMS: m2m100 is an older general model. Technical vocabulary will sometimes
     come out wrong. Mitigation (phase 2): the per-module glossary (module_glossary already
     exists): protect glossary terms during translation, or use a larger Workers AI model
     with the glossary in the prompt (costs more neurons: test before choosing).
   - Short slang and mixed-language sentences are the weak spot. The "see original"
     button is not optional.

--------------------------------------------------------------------------------
7. WHAT THE APP SHOWS
--------------------------------------------------------------------------------
  - Reader language == message language: show the text as is.
  - Translation ready: show it first, small label "Translated" + a tap for the original.
  - Translation not ready yet (first ~2 minutes): show the original with a quiet
    "translating..." marker; it updates by itself through realtime.
  - lang = 'und' or state = 'skipped'/'failed': show the original, no marker.
  - A "translate this" action calls request_translation() (also the fallback when a student
    changes language).
  - Optional later: on-device ML Kit as an offline fallback (30 MB model per language,
    Wi-Fi only, user choice).

--------------------------------------------------------------------------------
8. DATABASE CHANGES (file 09, written after you approve; all additive)
--------------------------------------------------------------------------------
  module_chat_messages  + translate_state (pending/working/done/skipped/failed),
                          translate_attempts, translate_after
  translation_requests  (message_id, lang, requested_by, created_at)   on-demand asks
  translation_cache     (text_hash, lang, body, created_at)
  translation_usage     (day, calls, chars, neurons_estimate)
  functions (service role only): module_reader_languages(module),
        claim_translation_batch(limit), save_translations(jsonb), release_translations(ids, delay)
  function (students):  request_translation(message, lang)
  post_chat_message: sets 'skipped' for file-only messages, otherwise 'pending'.
  Row security: everything above is invisible to students except what they already read
  through get_chat_messages().

--------------------------------------------------------------------------------
9. THE WORKER (micro m-translate)
--------------------------------------------------------------------------------
  - One Cloudflare Worker, cron trigger "* * * * *", Workers AI binding (no external key).
  - Talks to Supabase with a SECRET key stored as a Worker secret (never in the repo, never in
    the database). It only calls the service functions above.
  - Idempotent: running twice never duplicates a translation (upsert on message_id + lang).
  - One structured log line per run: claimed, translated, skipped, cached, failed, neurons.
  - Can be switched off without breaking the app (the app just shows originals).
  - Engine is behind one function translate(text, from, to) so Azure or a bigger model can be
    swapped in later without touching the rest.

--------------------------------------------------------------------------------
10. PRIVACY AND POLICY
--------------------------------------------------------------------------------
  Chat text is sent to Cloudflare to be translated. Check Cloudflare's current terms for how
  Workers AI treats customer content, and say in your privacy policy and in the Play "Data
  safety" form that messages are machine-translated by a third-party processor. Do not send
  names, emails or other profile data to the model: only the message text.

--------------------------------------------------------------------------------
11. TEST BEFORE LAUNCH
--------------------------------------------------------------------------------
  Take 30 REAL messages from Mining students (Arabic, French, mixed, Darija, with module
  terms). Translate them through the Worker, and have 2-3 students mark each result
  good / understandable / wrong. If "wrong" is above ~20% for Arabic<->French, switch the
  engine (larger model, or Azure F0) before the pilot.
