1. WHAT THE LIVE APP IS TODAY (differs from the v1 plan)
--------------------------------------------------------------------------------
Bottom navigation today (responsive_shell.dart): 4 items
  Home | Library | Messages | Marketplace
Home        : news + community feed ("Campus Now"), dining menus, exchange rates
Library     : study modules and resources (PDF/images per module)  <- seed of new MODULES
Messages    : direct messages between users about marketplace listings
Marketplace : student listings + Kampus Store (products, checkout, admin orders)
Languages   : onboarding offers EN and FR only (no Arabic UI yet)
Auth        : Google sign-in
Offline     : "drift" is in pubspec but is NOT used anywhere in lib/. There is no local
              content store yet (only feed cache + an outbox queue for likes/comments/posts).
Account deletion exists (delete_my_account RPC + R2 file purge). KEEP (store policy).

2.3 FILES / R2 (through a Cloudflare Worker, not Supabase Storage)
  Worker: https://upload.kampus-link.com   (POST multipart, Bearer = Supabase access token)
          POST /delete-user-files  (purges every file of the logged-in user)
  Folders the app sends:
      avatars      profile_setup_screen, avatar_picker
      community    community_screen, share_to_campus_now_screen, home_screen
      library      upload_resource_screen          <-- the DOCUMENTS (study resources)
      marketplace  create_listing_screen
  Returned URL is stored in the database (profiles.avatar_url, community_posts.image_url,
  marketplace_listings.image_urls, study_resources.file_urls).
  Worker 2: order-submit (workers.dev URL hard-coded in kampus_store_orders_screen.dart)
  Not in this repo: the source of both workers. NEEDED before any R2 change.

  >>> R2 WIPE WARNING <<<
  "Wipe all documents" must mean ONLY the `library` folder. avatars/, community/ and
  marketplace/ hold live profile photos, posts and Store/marketplace images referenced by
  rows in profiles, community_posts and marketplace_listings. Wiping the whole bucket
  would break every avatar and every Store listing image, including Kampus Store.
  After the library wipe, study_resources rows still point to deleted files: they must be
  deleted or flagged "unavailable" in the same operation (master plan section 7).

5. FINDINGS THAT CHANGE THE PLAN
--------------------------------------------------------------------------------
F1  R2 wipe = `library` folder only (section 2.3). Highest risk item.
F2  Kampus Store code (screens, orders, admin) also lives INSIDE this repo. If the
    standalone Store app has its own repo, confirm it, and confirm which tables/worker
    it uses before cutting anything here.
F3  A news pipeline exists outside the repo. The v1 plan has no news feed: decide to
    keep it running (data only) or retire it. Do not turn it off blind.
F4  Arabic is not supported in the UI today; v1 needs Arabic (RTL), French, English.
F5  Offline JSON store is greenfield (drift unused). Plan for it as new work.
F6  Security: anon key ships inside the app (.env is bundled as an asset). That is normal
    ONLY if RLS is correct on every table. Q2 is the first thing to read.
    Good: .env, keystore and google-services files are NOT tracked in git.
    Check: where the release keystore / upload key lives (you must keep using the same).
F7  Version: repo says 1.0.2+5. The next Play upload needs a versionCode higher than the
    highest ever uploaded (check Play Console, it may be above 5).
F8  The repo has a single commit. Before any deletion: tag the commit, make a backup
    branch, export the database and R2 (master plan 9.1).
F9  Hard-coded config in code: upload worker URL, order worker URL, WhatsApp numbers.
    Move to remote config so micros can change without an app release.
F10 CI deploys the WEB build to Cloudflare Pages on every push to main. Deleting
    features also changes the live website. Decide whether the web build stays.
F11 New tables must be added to delete_my_account and to the worker's delete-user-files
    (store policy: deletion must remove user data).
