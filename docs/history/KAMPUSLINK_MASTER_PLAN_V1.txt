1. PRODUCT IN ONE PAGE
--------------------------------------------------------------------------------
Name          : KampusLink
One line      : Where Algerian university students study, stay informed and
                connect, in one app that works on weak data.
First users   : Mining students, year 2 (one cohort, same modules, same exams).
Then          : Mining year 3 -> other mining years -> other departments in the
                same faculty -> other faculties -> other universities.
Focus         : The USER. No monetization work in v1.
Principles    : 1. Study first, social second.
                2. Offline-first. Light on data. Works on cheap Android phones.
                3. Under 3 taps from opening the app to studying.
                4. Verified students only. Trust is the product.
                5. Reward progress. Never guilt-trip absence.
                6. Three languages everywhere: Arabic (RTL), French, English.
                7. Everything that is content is JSON.

The app is an UPDATE of an existing, live Google Play app. It is NOT a new app.
See section 3 (identity lock) and section 9 (release rules).

4. THE CORE (SHARED, PROTECTED, "NEVER OVERLAP")
--------------------------------------------------------------------------------
The CORE is the only thing every lane depends on. Only the CORE OWNER lane may
edit it, and only after a logged founder approval.

  /core/schema/       database schema definitions + migration scripts
  /core/contracts/    API contracts (request/response shapes), error codes
  /core/content/      JSON content schemas (module, episode, flashcard, quiz...)
  /core/i18n/         translation keys (ar, fr, en) - key names are frozen
  /core/design/       design tokens (colors, spacing, type) as JSON
  /core/constants/    enums, IDs format, limits (file size, message length...)

Core rules:
  4.1  Contracts come BEFORE code. No lane builds against something that is not
       written in /core yet.
  4.2  Naming: snake_case for JSON keys and database columns; ids are prefixed
       (usr_, mod_, epi_, fc_, qz_, msg_, fil_); dates ISO 8601 UTC; languages
       are "ar", "fr", "en"; all text UTF-8.
  4.3  Every JSON content file has: schema_version, id, updated_at,
       content_hash. The app only downloads what changed.
  4.4  Backward compatibility: a change to the core must not break installed
       old app versions or the Kampus Store app (see section 5). Use
       EXPAND -> MIGRATE -> CONTRACT (section 6).
  4.5  Anything not listed in the core is private to its lane.

4B. MICROS (SMALL SINGLE-PURPOSE SERVICES)
--------------------------------------------------------------------------------
A micro is a small service that does ONE job: a Cloudflare Worker or a Supabase Edge
Function. The project already works this way (upload worker, order-submit worker).
Everything new that is not a screen or a table becomes a micro.

Rules:
  M1  One micro = one job, one owning lane, one contract in /core/contracts, one folder
      /micros/{name} in the repo.
  M2  A micro owns its tables (prefix) and its R2 prefix. Others use it only through its
      API or a view declared in /core. Nobody reads another micro's tables directly.
  M3  Micros never call each other. They talk through the database (queue/event rows)
      or through the app.
  M4  Every micro: checks the Supabase JWT, rate-limits, is idempotent (safe to run
      twice), uses a versioned route (/v1/...), and writes one structured log line.
  M5  Secrets only in the platform's secret store, never in the repo. Micro URLs live in
      remote config, not hard-coded in the app.
  M6  Every micro can be switched off without crashing the app (the app shows a
      graceful fallback).
  M7  Each micro must be covered by delete_my_account / delete-user-files if it stores
      user data.

The micros (build each one only when its phase arrives):
  m-upload        EXISTS. Extend: new prefixes (files/, content/), hash dedupe, type and
                  size limits, malware scan, delete-user-files covers new prefixes. LANE A
  m-content-sync  NEW. Per-module manifest (versions + hashes), signed download URLs,
                  delta updates for the offline JSON store. LANE A
  m-content-convert NEW. PDF -> JSON pipeline with a human review queue. LANE C
  m-translate     NEW. Translate-on-read with cache (message_translations), glossary per
                  module, "see original". LANE E
  m-notify        NEW. Push + email ladder with the hard stop (day 2/4/7/14/stop),
                  quiet hours, unsubscribe. LANE E
  m-moderation    NEW. Report queue, keyword filter, upload scan results. LANE A + E
  order-submit    EXISTS, belongs to Kampus Store. FROZEN: nobody touches it in v1.
Start with m-upload (extend) and m-content-sync only.

6. BACKEND CLEANUP - HOW TO DELETE WITHOUT BREAKING ANYTHING
--------------------------------------------------------------------------------
Golden rule: NOTHING is deleted until it is proven unused, backed up, and
deprecated for a waiting period.

Procedure for every table / column / function (EXPAND -> MIGRATE -> CONTRACT):
  Step 1  INVENTORY   List it in the dependency map (section 5.4).
  Step 2  PROVE       Search both codebases + check logs / usage counts.
                      Old installed app versions count as users.
  Step 3  BACKUP      Export the data. Verify the backup can be restored.
  Step 4  DEPRECATE   Mark as deprecated in /core/schema. Stop writing to it.
                      Keep it in place.
  Step 5  WAIT        Minimum 30 days AND until the old app versions that use
                      it are below an agreed share of active users.
  Step 6  DELETE      Drop it. Log it. Keep the backup for 90 days more.

Additive changes (new tables, new nullable columns) are always allowed first.
Never rename a column in place: add the new one, copy, switch, then retire.

Existing users and their data: every existing profile must still load after the
migration. New required fields (university, faculty, department, year, section,
language) are collected by onboarding for EXISTING users the first time they
open the new version; they are never required at the database level for old rows.

Kill switch / version gate: keep a remote config with "min_supported_version"
and "force_update" so very old versions can be given a friendly "please update"
screen after the transition period (never on day one).

8. ONBOARDING (MUST BE EXCELLENT - FIRST 90 SECONDS DECIDE EVERYTHING)
--------------------------------------------------------------------------------
Two paths, one flow:

NEW USER
  1. Splash, then LANGUAGE (Arabic / French / English). Big buttons, saved
     immediately, UI switches instantly (RTL for Arabic).
  2. Sign up / sign in (use the existing auth methods, do not invent new ones).
  3. Student details: university -> faculty -> department -> year -> section /
     group. For the pilot, preselect Mining / Year 2.
  4. Verification: university email OR student card photo (card photo deleted
     after review). Student can enter the app in "limited mode" while pending:
     read-only content, no chat posting, no uploads.
  5. Modules are assigned automatically from the details above. Show them as
     colored cards ("These are your modules").
  6. QUICK WIN in under 60 seconds: first swipeable flashcard from the student's
     own modules, then "Start your first study session" (timer begins).
  7. Notification permission is asked AFTER the quick win, with a reason in
     plain words. Never at launch.
  8. Finish: short tour hints (max 3), dismissible, shown once.

EXISTING USER (updated app)
  - Skip sign-up. Keep session and profile.
  - Ask only for what is missing (language, department/year/section).
  - Show a one-screen "What's new" explaining the new KampusLink.
  - Never wipe or reset their account, streak, or settings.

Onboarding rules: every step can be resumed after closing the app; progress is
saved; back button works; works offline up to the verification step; every
screen is available in 3 languages; track drop-off per step (section 13).

Done when: a new student reaches the first flashcard in under 60 seconds on a
mid-range Android phone, and an existing user reaches Home in under 20 seconds.

10. FEATURE SPECS (SHORT FORM - FULL CONTRACTS LIVE IN /core)
--------------------------------------------------------------------------------
10.1 HOME
  - Flashcard feed, vertical swipe, tap to flip, mixed across all modules.
  - Ordering: spaced repetition (simple Leitner box scheduling) + new cards +
    cards from recent mistakes. Balanced across modules.
  - Actions: like, comment, share (as image to WhatsApp), save.
  - Top: study timer pill + "Continue: {module}, episode {n}" card.
  - Social proof: "{n} students studying {module} now".
Done when: feed loads instantly from local JSON with no connection.

10.2 MODULES
  - Modules list: each module has its own accent color and progress.
  - Inside a module, 4 sections:
      EPISODES : the course as an ordered series of lessons, with progress,
                 unlocking one after the other, "continue where you stopped".
                 Each episode = readable blocks (text, formula, image, table),
                 its flashcards, its quiz, links to matching TD and TP.
      LIBRARY  : textbook, TDs, TPs, exams, student uploads. Filter by type.
                 Every uploaded file shows uploader, date, type, and badge
                 "verified" when a delegate/moderator approves it.
      QUIZZES  : MCQ, true/false, fill-in, numeric. Wrong answers create
                 flashcards automatically.
      CHAT     : the module chatroom (10.3).
  - "Download for offline" per module, with size shown before download.
Done when: a student downloads a module on Wi-Fi and studies it fully offline.

10.3 CHATROOM (ONE PER MODULE)
  - Text, replies, reactions, document and image upload.
  - Any document uploaded in chat is automatically created in the module
    Library (same file_hash = same file, no duplicates) and linked back to the
    message.
  - Auto-translation: store original text + detected language. Translate to
    each reader's language on first need, cache per (message, target language),
    never translate twice. Tap to see original.
  - Limits: known risk with Darija / Arabizi (Latin-letter Arabic); and mining
    terms need a per-module glossary so technical words stay consistent.
  - Safety: report, block, moderator tools, rate limits, file type and size
    limits, malware scan on uploads.
Done when: an Arabic message is readable in French and English within seconds
(online), and uploaded files appear in the Library without manual work.

10.4 TIMER AND STREAK
  - Starts when the app opens. Counts ACTIVE time only (pauses in background or
    after ~60 seconds without interaction).
  - Stored locally, synced when online. One streak per day of >= a small goal.
  - No guilt messages when the streak breaks; offer a recovery option instead.

10.5 PROFILE (BASIC)
  - Name, photo, university / faculty / department / year / section, language,
    theme (dark/light), study stats, streak, notification settings, account
    deletion, logout. Nothing else in v1.

10.6 NOTIFICATIONS AND EMAIL
  - Push first, email second. Content must be real information
    ("5 new cards in {module}"), never empty "come back" spam.
  - Re-engagement ladder when a student stops opening the app:
    day 2 -> day 4 -> day 7 -> day 14 -> STOP (hard stop, no more messages
    until they return on their own).
  - Quiet hours at night; full control in settings; one-tap unsubscribe.
  - Language of every message = the user's chosen language.

12. DESIGN SYSTEM (COLORS AND FEEL)
--------------------------------------------------------------------------------
  - Dark by default (night study), light option. Strong contrast.
  - One brand color + one accent color per module (students recognize modules
    by color). Suggested start: deep charcoal base, warm amber main accent,
    teal secondary. Final values are decided once and written to
    /core/design/tokens.json; nobody hardcodes colors in screens.
  - RTL-first layouts (Arabic is not an afterthought). Big tap targets.
  - Light animations only; the app must stay smooth on low-end phones.
  - Performance budget: cold start under 3 seconds on a mid-range phone,
    smooth 60 fps scrolling in the feed, no feature may break the budget.

13. METRICS (MEASURE THE USER, NOT VANITY)
--------------------------------------------------------------------------------
  - Onboarding: completion rate and drop-off per step; time to first flashcard
  - Retention: day-1 / day-7 / day-30
  - Focused study minutes per student per day (timer, active time only)
  - Share of the cohort opening a module every week
  - Flashcards studied, quizzes completed, uploads, chat messages per module
  - Quality: crash-free sessions, app size, startup time, data used per session
  - Monthly one-question survey: "Did KampusLink help you study better?"
  - Expansion gate (all must be true): >= 60% of the cohort installed and
    verified, day-7 retention > 30%, students add content themselves, several
    students say they would miss it, no major crash problems.

14. LANES (MULTI-AI WORKING RULES - SO NOTHING OVERLAPS)
--------------------------------------------------------------------------------
One lane = one owner at a time (an AI session or a human). A lane edits ONLY
its own paths. Lane names are fixed; which AI tool takes which lane can change.

  LANE A  CORE + BACKEND      owns /core/*, database migrations, API, R2 rules,
                              security rules, cleanup of backend tables
  LANE B  APP SHELL + DESIGN  owns app navigation, onboarding, Profile, design
                              system implementation, removal of marketplace code
  LANE C  CONTENT             owns the content pipeline, JSON files, R2 content
                              uploads, content log, glossary
  LANE D  LEARNING FEATURES   owns Home feed, Episodes, Quizzes, flashcard
                              scheduling, timer, offline storage
  LANE E  CHAT + LANGUAGES    owns chatrooms, uploads-to-library linking,
                              translation, i18n files, notifications and email
  LANE F  QA + RELEASE        owns tests, release builds, Play Console steps,
                              rollout checklist, crash monitoring (read-only on
                              all code, can only open issues)

Rules:
  14.1 Lanes talk to each other ONLY through /core contracts and the logs.
  14.2 Cross-lane need = write a REQUEST in the log addressed to that lane.
  14.3 Two lanes must never edit the same file. If it happens, the later one
       stops, logs a CONFLICT, and waits for the founder.
  14.4 Shared files (build config, dependency list) belong to LANE B; others
       request additions.
  14.5 Every AI starts each session with the "Session start prompt" in
       section 16 and ends with a log entry.
  14.6 A new AI taking over a lane must read the lane's last 30 log entries
       before touching anything.
  14.7 Branching: one branch per lane per task; merged only by the founder
       or LANE F after checks pass.
