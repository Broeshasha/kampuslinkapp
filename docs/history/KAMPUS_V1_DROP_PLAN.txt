0. READ THIS FIRST - SECURITY (do BEFORE any cleanup)

S1  CRITICAL  A service_role key is written in plain text inside the function
              public.call_send_push (it came back in the Q3 result). That key bypasses
              all row security. Treat it as compromised: it has now been pasted in a
              chat. On top of that, anon AND authenticated can EXECUTE that function
              through the public API, so anyone holding the app's anon key can make your
              project send push notifications to anyone, using your service key.
              FIX ORDER (each step is safe on its own):
                a) make the 5 notification trigger functions run as definer, so they
                   keep working after step b
                b) revoke execute on call_send_push from anon / authenticated / public
                c) replace the function body so the key lives in Supabase Vault
                d) rotate the service key and update everything that uses it
                   (edge functions, scrapers/n8n/workers, the Vault secret)
              CAUTION on d): the app ships the anon key inside every installed APK. If
              you rotate the project's legacy JWT secret, the anon key changes too and
              EVERY installed app and the Kampus Store break. Use Supabase's separate
              secret-key mechanism if your project has it, or schedule a JWT-secret
              rotation together with a forced app update. Read Supabase's current docs
              before choosing. Read the send-push edge function first (how does it
              verify its caller?).
              SQL (steps a-c; put the NEW key in Vault from the SQL editor yourself,
              never paste a key into chat or into a file):
                alter function public.trg_notify_comment()      security definer set search_path = public;
                alter function public.trg_notify_comment_like() security definer set search_path = public;
                alter function public.trg_notify_like()         security definer set search_path = public;
                alter function public.trg_notify_message()      security definer set search_path = public;
                alter function public.trg_notify_new_post()     security definer set search_path = public;

                revoke execute on function public.call_send_push(jsonb) from public, anon, authenticated;

                -- after the new key exists in Vault under the name 'send_push_key':
                create or replace function public.call_send_push(payload jsonb)
                returns void language plpgsql security definer set search_path = public as $$
                declare k text;
                begin
                  select decrypted_secret into k from vault.decrypted_secrets where name = 'send_push_key';
                  perform net.http_post(
                    url     := 'https://<YOUR-PROJECT-REF>.supabase.co/functions/v1/send-push',
                    headers := jsonb_build_object('Content-Type','application/json','Authorization','Bearer '||k),
                    body    := payload);
                end $$;
              TEST: like a post / send a message in the app, confirm a push still arrives.

S2  HIGH      notifications has row security OFF while anon and authenticated hold full
              table rights. Anyone with the anon key can read, change or delete all 143
              notifications (user ids + message previews). Two other tables are also
              open: kampus_store_import_queue (412 rows) and domains (8 rows).
              SQL:
                alter table public.notifications enable row level security;
                create policy "own notifications read"   on public.notifications
                  for select to authenticated using (auth.uid() = user_id);
                create policy "own notifications update" on public.notifications
                  for update to authenticated using (auth.uid() = user_id) with check (auth.uid() = user_id);
                alter table public.kampus_store_import_queue enable row level security;  -- no policy: service role only
                alter table public.domains enable row level security;
                create policy "domains read" on public.domains for select to anon, authenticated using (true);
              TEST: notifications screen + unread badge still work; Store import job still runs
              (service role bypasses row security); Store admin pages still load.

S3  HIGH?     The view pending_kampus_store_orders holds buyer name, phone and address and
              anon/authenticated both have SELECT on it. If the view is not
              security_invoker it runs as its owner and BYPASSES row security, so anyone
              could read customer data. Round-2 query R2 shows the view options.
              If R2 does not show security_invoker=true, add an admin gate (keeps the
              Store admin screen working, hides everything from everybody else):
                create or replace view public.pending_kampus_store_orders as
                 select o.id, o.buyer_full_name, o.buyer_phone, o.buyer_wilaya, o.buyer_commune,
                        o.buyer_address, o.quantity, o.status, o.created_at,
                        p.display_name as product_display_name, p.sell_price, o.referral_code
                   from kampus_store_orders o
                   join kampus_store_products p on p.id = o.product_id
                  where o.status in ('pending_call','called') and ks_is_admin()
                  order by o.created_at desc;
              This is a STORE object: apply it, then open the Store admin as admin and as a
              normal user to confirm the right result in each case.

S4  MEDIUM    get_message_threads(viewer_id) is SECURITY DEFINER and executable by anon, and
              it trusts the viewer_id you pass in. Anyone can pass someone else's id and
              read that person's last message in every conversation. (The other viewer_id
              functions only leak public profile data.) Guard it:
                create or replace function public.get_message_threads(viewer_id uuid)
                returns table(other_user_id uuid, other_username text, other_avatar_url text,
                              other_avatar_blurhash text, last_message text,
                              last_message_at timestamptz, unread_count bigint)
                language sql security definer set search_path = public as $$
                  with thread_partners as (
                    select distinct case when sender_id = viewer_id then recipient_id else sender_id end as other_id
                    from messages
                    where (sender_id = viewer_id or recipient_id = viewer_id)
                      and viewer_id = auth.uid()                      -- the guard
                  ), latest as (
                    select tp.other_id,
                      (select content from messages m where (m.sender_id = viewer_id and m.recipient_id = tp.other_id)
                         or (m.sender_id = tp.other_id and m.recipient_id = viewer_id) order by m.created_at desc limit 1) as last_message,
                      (select created_at from messages m where (m.sender_id = viewer_id and m.recipient_id = tp.other_id)
                         or (m.sender_id = tp.other_id and m.recipient_id = viewer_id) order by m.created_at desc limit 1) as last_message_at,
                      (select count(*) from messages m where m.sender_id = tp.other_id and m.recipient_id = viewer_id and m.read_at is null) as unread_count
                    from thread_partners tp)
                  select l.other_id, p.username, p.avatar_url, p.avatar_blurhash, l.last_message, l.last_message_at, l.unread_count
                  from latest l join profiles p on p.id = l.other_id
                  order by l.last_message_at desc;
                $$;
                revoke execute on function public.get_message_threads(uuid) from anon;
              The app passes its own id, so nothing changes for real users.

S5  MEDIUM    Every signed-in user can read every other user's profiles row, including
              fcm_token (push address) and is_admin. v1 moves tokens to a private table
              (section 2). Do not patch with column grants now: old app versions may use
              select('*') and would break.

S6  MEDIUM    Account deletion is incomplete (store-policy risk). delete_my_account does
              NOT remove: post_likes, post_comments, post_comment_likes, study_bookmarks,
              study_resource_upvotes, study_stats, study_resources they uploaded, or
              kampus_store_orders (student_id points to auth.users with no ON DELETE).
              A user who liked a news post, bookmarked or uploaded a file, or ordered from
              the Store will hit a foreign-key error and the deletion FAILS. Rewrite it in
              the v1 migration (section 2). For Store orders: set student_id = null
              (keep the order for accounting) - needs Store owner approval.

S7  LOW       anon and authenticated hold TRUNCATE / TRIGGER / REFERENCES on every table
              (Supabase defaults). The REST API cannot reach TRUNCATE, so row security is
              what protects you, but revoke these anyway during hardening.

3. THE TWO-TRACK STRATEGY (THIS SOLVES "DROP FIRST" WITHOUT BREAKING USERS)
--------------------------------------------------------------------------------
Problem: if we drop backend objects now, the LIVE Play app (1.0.2) breaks for its users
until v1 ships, and an update that shows an empty home screen cannot be published (it
would be an app with almost no function; a store-policy and review risk, and it takes
features away from existing users).
Solution: build v1 on a DEV COPY, and replay the exact same drops on PROD at a gate.

TRACK DEV (starts now, drops happen here immediately)
  D1  Create a second Supabase project "kampuslink-dev" from the PROD schema (CLI schema
      dump -> restore) plus REFERENCE data only: universities, specialities, domains,
      study_modules, wilayas, dz_communes. No user data, no orders, no R2 files.
      A separate dev R2 bucket (or prefix) and a dev copy of the upload worker.
  D2  Run the whole drop plan (section 4) on DEV. Each batch ends with the STORE SMOKE
      TEST (section 5). DEV is where the "empty slate" lives.
  D3  Point the purged front-end (section 6) at DEV through its .env. PROD keys stay out.
  D4  Build v1 on DEV, phase by phase, with the lanes of the master plan.
TRACK PROD (only gated actions)
  P1  Security fixes S1-S4 now (they are small and independent).
  P2  Archive (section 4, stage 0): tables copied into an archive schema, R2 library
      copied to a cold bucket.
  P3  Additive migrations (new tables/columns) when the closed beta starts.
  P4  DROPS only at gate G4 (section 4) after v1 is rolled out and old versions are gone.
