7. OFFLINE AND RESUME LOGIC (the heart of the app)
--------------------------------------------------------------------------------
  7.1 THE APP READS ONLY THE LOCAL DATABASE. The network only fills it and drains the outbox.
  7.2 LOCAL TABLES (Drift): modules, lessons (+ per-language title/summary/blocks as JSON text), cards,
      questions, resources (meta) + file cache index, glossary, card_progress, lesson_progress,
      reading_position, study_daily, stats, chat_cache (last 100 messages per module), outbox, settings,
      content_versions.
  7.3 DOWNLOAD UNIT = module bundle. Flow: get_my_modules() -> for each module compare server version
      with local version -> if newer (or never downloaded) call get_module_bundle(module, [uiLang, contentLang])
      -> replace the module's rows in one transaction. Parse in an isolate. Show per-module state:
      not downloaded | downloading (progress) | up to date | update available | failed (retry).
      Big downloads only on Wi-Fi by default (setting). PDFs/files download on demand into the app
      documents folder, named by hash, with a storage cap (LRU, default 500 MB, user can clear).
  7.4 WHEN TO SYNC: app start, app resume, connectivity regained, pull-to-refresh, every 15 min while
      active, and right after the user finishes an action (outbox flush).
  7.5 OUTBOX. Every write that must reach the server is saved FIRST in the outbox with a new uuid op_id:
        review, answer, lesson_done, study_time, reading_position, like, save  -> sent in batches of <= 200
        through sync_progress() (replay-safe);
        chat message (client_id), comment, upvote, report, block, settings -> their own calls, each idempotent
        or tolerant of a retry.
      Flush rules: oldest first; on success delete; "duplicate" = delete; "rejected" = delete + log the message;
      network error = keep + exponential backoff (5 s, 30 s, 2 min, 10 min, then every 15 min);
      401 = stop and ask to sign in again (outbox kept). The UI shows "n waiting to sync" quietly in Profile.
  7.6 LOCAL-FIRST PROGRESS. A review changes the local card box/due date immediately (same Leitner numbers
      as the server: 10 min / 1 d / 3 d / 7 d / 14 d), so the feed works offline. After a successful sync
      the app pulls the server's own rows (learn_card_progress, learn_lesson_progress,
      learn_reading_position, study_stats, study_daily - own-row reads) and merges: card progress = the row
      with the newest last_reviewed_at, lesson progress = union, reading position = newest updated_at,
      streak/xp = server value. Content is always server-wins.
  7.7 RESUME ("where I stopped")
      - The lesson reader reports the id of the first visible block + progress (0..1). Save locally on
        every scroll end (debounced 1.5 s), when leaving the screen and when the app goes to background;
        queue reading_position in the outbox (latest per lesson only: replace, do not pile up).
      - Opening a lesson jumps to the saved block id (works across languages: ids are the same). A small
        "Back to where you stopped" chip appears if the student scrolls away.
      - HOME "Continue" card = most recent unfinished lesson (progress 0.02-0.98, not completed), from the
        local table; with no history: the first unread lesson of the module the student opened last.
      - MODULES list: progress ring per module and per lesson (completed / in progress / new).
      - Quiz: answered questions are recorded when answered; an interrupted quiz resumes at the first
        unanswered question. Completed lesson = lesson_done op.
      - Study timer: counts only ACTIVE time (screen on, app in foreground, a touch or scroll in the last
        60 s); flush log_study_time every 30-60 s of active time, and on pause. Never counts in background.
  7.8 CHAT OFFLINE: cached messages stay readable; sending offline queues a message with a client_id and
      shows it as "sending..."; after 3 failed tries it shows "tap to retry". Translations arrive by
      realtime or on next open; the original is always shown first when no translation exists.
  7.9 CONTENT VERSIONING: bundles carry schema_version. An app that meets a newer schema_version than it
      knows keeps the old local content, shows "update the app for new content", and keeps working.
  7.10 FIRST RUN OFFLINE: the app opens, shows a friendly "connect once to download your modules" state;
      it never shows an empty screen without explanation.

8. CONTENT SYSTEM (summary; the full spec is docs/CONTENT_FORMAT.txt)
--------------------------------------------------------------------------------
  Pipeline  PDF -> AI-assisted extraction to chapter JSON (3 languages, block ids, glossary, quality issues)
            -> validate (tools/content/validate) -> human review (issues, Arabic, formulas) -> rights recorded
            -> import as DRAFT -> cards + quiz generated and reviewed -> publish -> module version bumps ->
            apps sync. The database refuses to publish a lesson with unknown rights or open review issues.
  Size      one chapter = about 60 KB per language (12 KB gz); a module of 8 chapters = about 0.8 MB for
            two languages. Offline is cheap.
  Targets   the sample chapter (Chimie minerale, chapter II) becomes about 5 episodes with 6-10 cards and
            3-5 questions each. Pilot goal: 3 complete modules before launch (Chimie minerale, Maths 3,
            Mecanique des fluides), then 1-2 modules a week.
  Roles     Lane C builds and runs the tools; reviewers are students who passed the subject; the founder
            decides rights. Every item is logged in KAMPUS_CONTENT_LOG.txt with source, rights, reviewer.
  Flagged   the sample has 30 unresolved issues (13 review_required) in the ORIGINAL course. They are
            resolved by a person before publishing, never auto-fixed by an AI.

11. WORKING PROTOCOL WITH THE AIs (how the founder runs the team)
--------------------------------------------------------------------------------
  The loop is:  AI gives PowerShell -> founder pastes it -> founder pastes the output back -> AI checks and
  gives the next step.  The AI never assumes a step worked: it reads the output first.
  START OF EVERY SESSION: the founder gives the AI the repo access (or the zip) and pastes the P0
  prompt + the one work-package prompt from docs/PROMPTS.txt. The AI must read AGENTS.md, this plan,
  the contracts and the last 20 log entries BEFORE writing code, then say in 5 lines what it understood.
  A STEP is small: one idea, at most 5 files, at most ~150 lines per file, verified at the end.
  POWERSHELL RULES the AIs must follow:
   - Start with  cd <repo folder>  and  . .\docs\tools\ps-helpers.ps1  (helpers: Write-Kampus,
     Replace-InFile, Step-Check, Step-Commit). Write files through Write-Kampus (UTF-8 without BOM).
   - Use single-quoted here-strings @' ... '@ for code (no variable expansion). The closing '@ must start
     the line. Split big files into several pastes (a file can be created in parts with -Append).
   - Edit existing files with Replace-InFile (exact text must occur once) instead of rewriting them.
   - Every step ends with  Step-Check  (pub get, format, analyze, test) and then  Step-Commit "<message>".
   - Each step says what the founder should SEE (expected output / screen) and what to paste back.
   - Never ask the founder to edit code by hand, and never put secrets in a command.
  BRANCHES: v1-reset is the integration branch. Each work package works on  wp/<number>-<name>  and
  merges to v1-reset only after acceptance. main is untouched until the release (it deploys the web
  build and feeds Play).
  LOGS (append-only, in docs/logs/): APP_LOG (every session ends with an entry), CONTENT_LOG, DECISIONS.
  When an AI needs a contract change it writes a CORE CHANGE REQUEST in DECISIONS and stops that part.
  REVIEW: the lead planner (Claude) reviews each accepted WP against the plan; Lane F re-runs the checks.
  If two AIs disagree, the contract files decide; if they are silent, the founder decides and logs it.
